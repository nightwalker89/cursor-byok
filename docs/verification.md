## Unit and Syntax Checks

```bash
npm run check          # scripts/check-syntax.js + ESLint + node --test
npm test               # node --test only
```

`scripts/check-syntax.js` walks `src/`, `scripts/`, and `tests/`, running
`node --check` on every `.js` file as a parse gate; the Node built-in tests
grey-box test the hook, server, provider loops, protocol helpers, and installer
with in-memory fakes.

## Install Check

```bash
npm run preflight:cursor
npm run install:cursor
```

Then restart Cursor and verify:

- `preflight:cursor` reports at least one supported hook point and does not write
  the target files.
- `~/.cursor/extensions/starduster.cursor-byok-1.0.0` exists.
- The Cursor extension registry (`~/.cursor/extensions/extensions.json`) contains
  `starduster.cursor-byok` and no legacy BYOK entries.
- `workbench.desktop.main.js` contains exactly one `CURSOR-BYOK-HOOK-V2-START`
  marker (re-running the installer is idempotent — it strips before inserting).
- On a **clean** Cursor target, `~/.cursor-byok/workbench-hook-state.json` and
  `~/.cursor-byok/workbench-backups/` exist after install.
- `http://127.0.0.1:<active-port>/byok/health` returns
  `{"ok":true,"byokMode":…,"workspaceRoots":[…]}` when the server is running.
  Multi-window installs may also include `windowId` and `windowScoped`.
  The active port may be the configured base port or the next available probed
  port.
- If you need to validate rollback, run `npm run restore:cursor` against a
  disposable or freshly reinstalled Cursor target and confirm the backed-up
  workbench file hash returns to its pre-install value.

## UI Regression

Use a configured BYOK model and exercise real Cursor tools from the chat UI. A
minimum regression prompt should require: write a temporary file → read it with
explicit `offset` and `limit` → edit or ApplyPatch it → read again with explicit
`offset`/`limit` → grep for the edited content → glob for the file → delete it.

Collect evidence from the `Cursor BYOK` output channel / `~/.cursor-byok/cursor-byok.log`
(`LocalLog`, log labels in `src/server/*`):

- `"BYOK run"` — the run uses the expected `provider`/`model`/`toolCount`.
- `"BYOK tool call"` — Read calls include `argumentKeys` with `path`/`offset`/`limit`
  and `readHasPath`/`readHasOffset`/`readHasLimit` true; `requestId` is distinct
  from `conversationId`.
- `"BYOK Cursor exec result"` / `"BYOK returning Cursor exec result"` —
  `messageCase:"readResult"`, `resultCase:"success"`, nonzero `contentLength` for
  nonempty files (`summarizeExecResult`).
- Edit bridge emits internal `<id>-read`/`<id>-write` exec ids and a final
  `editResult`.
- Grep/Glob/Delete return success cases; no timeout, malformed result, unexpected
  custom tool card, or native Shell substitution for the file tools above.

Check official models separately: selecting an official Cursor model must **not**
call the BYOK provider adapter (no `"BYOK run"` log; traffic falls through to
`api2.cursor.sh`).
